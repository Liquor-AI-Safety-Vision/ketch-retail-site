# 16 cameras on the split architecture — L40S, 2026-08-25

First 16-camera measurement of the four-tier split pipeline taken **after** the
`cap_native_threads` fix. Every number recorded before this date was measured
with the BLAS/OpenMP caps silently not applied, so none of them are comparable
to these.

Instance: vast.ai L40S (46 GB), `/venv/main/bin/python` 3.12.13, 192 logical
CPUs visible to `os.cpu_count()`.
Manifest: `ai/config/stores/local_dev_store_16cams.json`, all 16 cameras.

## Correctness first

| check | result |
|---|---|
| `compileall` over `src`, `tools`, `tests` | clean |
| CPU suite (tier_status, access_schedule, no_unbound_names, fsm_globals_guard, frame_ring, split_cleanup) | 25 passed |
| `test_split_pipeline.py` — split output vs in-process tracking | passed |

The equivalence test is the one that matters: decode → infer → business through
the real four tiers produces the same frame count, the same per-frame live-track
counts and the same number of created tracks as calling pose/ReID/tracker
directly in one process. It had not been run since any of the fixes made while
the instance was off.

Full-stack output also matches the recorded baseline
(`bench16_thread_posew4_20260824_clean.json`): **3840 frames, 0 alerts** in both.
Zero alerts is this footage's real baseline, not a regression — the clean
baseline file records the same. (The other two `bench16_*.json` files on the
instance are truncated mid-write and cannot be parsed; only the `_clean` one is
usable.)

## Duration matters more than it looks

At `--duration 15` the full stack reports **80.52 FPS**; at `--duration 60` the
same topology reports **122.22 FPS**. The 15s run is not a slower pipeline, it
is a shorter one: wall was 11.9s while every business thread reported only ~6.8s
of work, so a third of that run is ramp-up and drain. Tier ladders and topology
comparisons must use 60s. 15s runs stay useful for "does it work at 16 cameras",
which is what they are for.

Model load is excluded from the clock in every number below, and is reported
separately because it scales with inference process count.

## Tier ladder — 16 cameras, 60s, 3840 frames

| layer | topology | FPS |
|---|---|---|
| decode only | 8 decoders | 173.18 |
| decode only | 16 decoders | 183.93 |
| decode + infer | 8 dec, 2×8 lanes | 131.09 |
| full stack | 8 dec, 2×8 lanes, 4 business | **122.22** |

Reading the ladder: inference is the binding tier. It costs 184 → 131 (−29%).
The business tier costs 131 → 122 (−7%), which is cheap — it is not worth
optimising next. Decode has ~1.5× headroom over the full stack, so it is not the
constraint today, but it is close enough that it becomes the wall if inference
improves much.

Decode is flat across 4 / 8 / 16 decoder processes (173.06 / 173.18 / 183.93),
so decode parallelism is not what limits it. Note `VirtualVideoStreamSource`
`grab()`s every source frame and only `retrieve()`s the ones it emits
(`virtual_video_stream.py:199-230`), so at a 3-5 fps target against ~25-30 fps
footage it walks 6-10× more frames than the FPS figure suggests.

## Inference topology — full stack, 16 cameras, 60s

16 cameras allow at most 16 lanes; `_validate_topology` rejects more (3×8 = 24
lanes raises, correctly — idle lanes would silently measure a topology other
than the one requested).

| inferers × threads | FPS | model load |
|---|---|---|
| 1 × 16 | 81.65 | 12.6 s |
| **2 × 8** | **122.22** | 19.1 s |
| 4 × 4 | 111.98 | 32.6 s |
| 8 × 2 | 105.77 | 68.8 s |

**2 × 8 is the optimum**, and the curve has a clear peak on both sides of it:
one process is GIL-bound, and past two processes the per-process CUDA context and
scheduling cost outweighs the added parallelism. Model load grows ~7-8s per extra
inference process (CUDA context + model init), which is why 8×2 pays 68.8s before
the clock even starts.

This supersedes the earlier "2 threads per inference process is optimal" and the
"one process saturates at ~4 lanes" conclusions. Both were measured under the
thread-cap bug and neither survives it.

## Balancing the till load across both inference processes is slower

`_shard` strides and the manifest lists cameras in blocks by type, so all four
counter cameras land on `inference-0`: it does 100% of the till work and
`inference-1` does none. That looks like an obvious thing to fix, on the tier
that is already the bottleneck. It is not.

| camera order | till split | run 1 | run 2 |
|---|---|---|---|
| manifest (blocked) | 4 / 0 | **144.56** | **138.21** |
| roundrobin (interleaved) | 2 / 2 | 132.31 | 131.55 |

Balancing costs ~7%, reproducibly. The reason is an earlier measurement:
interleaving three models inflates each by ~55%. Under manifest order
`inference-1` interleaves only two models and escapes that penalty entirely;
balancing makes *both* processes interleave three, which doubles the cost
rather than removing it.

The general lesson for this tier: keeping like work together beats dividing
camera counts evenly. `--camera-order roundrobin` stays in the tool so this
negative result can be reproduced, not because it should be used.

## ReID's fixed batch=16 looks wasteful and is not

The Embedder (OSNet-x0.25, ReID) has no shared batch runner like pose/till --
each lane builds a private instance and calls `sess.run` immediately, padding
every call up to a fixed batch of 16 because the exported graph pins that
dimension. At ~2 boxes/frame on this footage that pads ~87.5% of every call
with zero rows, which looks like the same waste `pose_max_batch`/`pad_batch`
already fixed elsewhere.

It is not free to fix, and here fixing it is a net loss. A batch-dynamic
export of the same weights, isolated (`diag_infer_modules.py --module reid`,
real per-frame box counts):

| model | threads=1 | threads=2 | threads=4 |
|---|---|---|---|
| fixed batch=16 | 106-113 calls/s | 168-192 | 275-298 |
| dynamic batch | 38 calls/s | 73 | 80 |

3.5-7x slower, not faster. Isolating per-call latency as box count changes
confirms why: dynamic batch pays the CUDA EP's per-shape re-plan on almost
every call (~200-220ms) and only avoids it when consecutive calls happen to
have the same box count; fixed batch never re-plans because the shape never
changes (a steady 6.5-9.4ms regardless of real box count). This is the exact
failure mode already documented for pose (`pad_batch`) and till
(`till_max_batch=1`) -- it had just not been checked for ReID. OSNet is small
enough (0.9MB weights) that the ~150-200ms re-plan tax dwarfs the few
milliseconds the padding wastes.

So the fixed-batch model and the unpadded-looking call in `Embedder.__call__`
stay as they are. The `-dyn` export is not worth keeping.

## Reproducing

```
python ai/tools/diag_split_tiers.py --layer all --cameras 16 --duration 60 \
    --decoders 8 --inferers 2 --infer-threads 8 --business 4
```

Swap `--layer` for `decode` or `infer` to walk the ladder. Always 16 cameras —
a smaller slice changes the load mix, because the four counter cameras carry all
of the till work.
